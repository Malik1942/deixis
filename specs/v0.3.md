# Locant v0.3: usable by someone else

**Scope of this spec:** the product surface a second user meets: mode that infers itself, a Settings window, and the floating ball as a launcher. Tagged `v0.3` at the end. The MCP server (v0.2 slot 3) and Snap/Text/Color/Cut with the ring stay after it.
**Revision:** Sep 13, 2026, after v0.2-region.
**Out of scope:** the press-and-hold ring (needs Snap and Text to exist), Color, Cut, lifecycle cleanup and retention, Sparkle, URL scheme, Safari/Chrome URL read (still deferred).

Read `CLAUDE.md` first, then `specs/v0.1.md` and `specs/v0.2.md`. This file is the task contract. Visuals come from `docs/PRD.md` §6; do not invent values.

## 1. The constraint this removes

`mode` decides whether a capture is a fix to the user's own code or a reference to someone else's. In v0.1 and v0.2 the list of the user's apps is hard-coded to two bundle ids, so Locant only works for Malik. A universal product cannot ask every user to register their apps before the first capture. Two things fix that:

1. **Mode is inferred, not configured.** Signals that need nothing from the user, in order (section 4).
2. **Settings is an override, not a prerequisite.** A fresh install works with every default; My Apps exists for the cases inference misses.

Mode also matters less than it looks: it changes the payload's wording and order only. A wrong inference costs one line of ordering, never information. Verify (v0.4) will need the project path, and the same inference yields it.

## 1a. Direction (Malik, Sep 13)

Beyond v0.3: Locant should be able to grab everything shown on screen, with context and not only pixels. The fallback ladder (element → cluster → drawn frame → text and neighbors → image) is the spine of that; later slots widen each rung rather than add modes.

## 4. Mode inference (R17)

Input: the source app's bundle id, the running executable's path, whether the front app is the Simulator, the URL host when known, and the My Apps list. Output: `mode` and an optional `projectRoot` path. Evaluated top to bottom; the first hit wins.

1. **My Apps** contains the bundle id (or the simulated app's bundle id) → `fix`. Manual override always wins.
2. **Simulator** → `fix`. Only builds the user made can run there; App Store apps cannot be installed. (Reverses the v0.1 amendment: the "someone else's app in the Simulator" case is rare and one line of ordering.) `projectRoot` from rule 4 applied to the simulated app's bundle path when it is under `DerivedData`.
3. **Localhost** URL host (`localhost`, `127.0.0.1`, `*.local`, `0.0.0.0`) → `fix`. Dormant until the URL read lands.
4. **Built here.** The app's bundle path is under `~/Library/Developer/Xcode/DerivedData/`, or any ancestor directory of the bundle contains an `.xcodeproj`, `.xcworkspace`, or `Package.swift` → `fix`, `projectRoot` is that directory. For DerivedData builds, the project is found through the `info.plist` of the DerivedData folder (`WorkspacePath`), when present.
5. **Signed by the user.** The app's code signature Team ID equals the Team ID of any Apple Development identity in the user's keychain → `fix`. Public API: `SecStaticCodeCreateWithPath`, `SecCodeCopySigningInformation`, identities via `SecItemCopyMatching`. Skipped silently when the keychain query fails or prompts.
6. Else `reference`.

`projectRoot` is written to the sidecar as an optional `source.projectRoot` string (schema additive) and to the payload as `Project: /path` when known. Never guessed: absent when no rule produced it.

Tests (pure, paths and ids as inputs): each rule in isolation, the order, and the project-root discovery on a temp directory tree.

## 5. Preferences (R18)

Typed wrapper over `UserDefaults.standard`, owned by `AppState` and passed to whoever needs a value. Keys and defaults:

| Key | Type | Default |
|---|---|---|
| `hotkeyModifier` | `control` / `option` / `shift` / `command` / `rightCommand` | `control` |
| `captureFolder` | path string | `~/Pictures/Locant` |
| `ballEnabled` | Bool | `true` |
| `ballPosition` | `{x, y}` in AppKit screen points, or absent | absent → lower right (PRD P1.11) |
| `myApps` | `[String]` bundle ids | `[]` |
| `organization` | `none` / `byApp` / `byProject` / `byMonth` | `none` |

Changing the hotkey restarts the monitor; changing the folder is picked up at the next write; the ball toggle shows or hides the ball immediately. No migration: v0.1 and v0.2 wrote nothing.

## 6. Settings window (R19)

A SwiftUI `Settings` scene, per PRD §6.3 "Settings" and the `settings.*` tokens, with two tabs:

**General** (`gearshape`)
- Hotkey: `Picker` (menu style) with "Double-tap Control" … "Double-tap Right Command". Footnote: "Double-tap Command is used by Codex; double-tap Option by Claude Desktop."
- Capture folder: path in a read-only `TextField` plus a bordered "Choose…" button opening `NSOpenPanel` for folders. Footnote: "Each capture writes a PNG and a JSON sidecar here."
- Floating ball: `Toggle`. Footnote: "A quiet disc that wakes when you approach. Click it to point. The hotkey works either way."

**My Apps** (`app.badge.checkmark`)
- A grouped `Form` like the other tabs (revised Sep 14, 2026): one row per app with its icon, name, and bundle id (only the id, and a plain app icon, when the app is not on this Mac) and a Remove button trailing; a second group adds one with Choose… (`NSOpenPanel` for `.app` bundles, reads the bundle id) or a typed bundle id with Add. Footnote: "Locant already treats apps you build (Simulator, Xcode builds, your signing identity) as yours. Add anything it misses."

Opened from the menu bar item "Settings…" (⌘,) via `showSettingsWindow:`. The window opens 520 pt wide and resizes from 480×360 (size remembered; it can be minimized, and ⌘H puts it away without hiding the ball), `Form` with `.formStyle(.grouped)`, system controls only, no header art, no app name in the body. Menu bar order becomes: Capture (⌃⌃), Open capture folder, Settings…, Quit.

Requires `LocantApp` to become a SwiftUI `App`; the `NSApplicationDelegate` keeps the status item, permission alerts, and `AppState`. LSUIElement stays. No other scene.

## 6a. Capture organization (R21, added Sep 13 after Malik's request)

Finder tags are always written on the PNG and the JSON: `Locant`, the app name, `fix` or `reference`, and the project folder name when inference found one. Finder, Raycast, and Eagle then search and group captures without any structure of ours. An "Organize captures" picker in General adds subfolders for people who think in folders: one folder (default), by app (the app slug), by project (the project folder name, else the app slug), by month (`yyyy-MM` from the id). Filenames stay the same everywhere. Consumers that read the folder (the MCP server, Verify) must read it recursively. Preference key `organization`, default `none`.

Tests: `FileStoreTests` 3. folder per organization and tag list; a written file carries the tags.

## 7. Floating ball (R20)

Per PRD P1.11 and §6.2 `ball.*` tokens. A `nonactivatingPanel` at `.floating` level, `canJoinAllSpaces`, no shadow, excluded from captures through the existing own-windows filter.

- **Rest:** 28 pt disc, `.hudWindow` material, `labelColor` at 10 percent, 1 px `separatorColor` edge, no icon. Glow: fill drifts 8 → 14 → 8 percent over 6 s, continuous, off under Reduce Motion.
- **Docked:** after 5 s without interaction, slides to the nearest screen edge and shows as a half-disc at 6 percent; glow continues. Position remembered in `ballPosition` across launches.
- **Awake:** cursor within 80 pt (global mouse-moved monitor, throttled): opacity to 100 percent in 200 ms, `hand.point.up.left` fades in at center, a docked ball slides back out.
- **Ready:** cursor over the ball: edge becomes `controlAccentColor`, cursor the pointing hand.
- **Click:** starts Point exactly as the hotkey does (context is collected before the overlay, so the front app is the one the user was looking at; the ball never activates Locant).
- **Drag:** moves the ball; a drag is not a click (6 pt threshold, as the marquee).
- **Press and hold:** nothing in v0.3. The ring arrives with Snap and Text.
- **First launch:** on, near the lower-right edge, one 800 ms fade-in. Settings turns it off. The menu bar item stays the reliable entry.

Decided by Malik (Sep 13): on by default, placed at the lower right on first launch, with a Settings toggle to turn it off. The PRD's "off by default" lines (P1.11, open question 9) are superseded and should be updated at its next revision.

## 8. Tests

`ModeInferenceTests`: 1. My Apps wins; 2. Simulator is fix; 3. localhost hosts; 4. DerivedData path is fix; 5. ancestor with `.xcodeproj` gives fix and the project root; 6. matching Team ID is fix (injected identity list); 7. none of the above is reference with no project root.
`PreferencesTests`: 1. defaults when nothing is stored; 2. round trip of every key through an isolated `UserDefaults` suite; 3. `ballPosition` absent → nil.
No UI tests for Settings or the ball (v0.1 rule: pure functions get tests, UI does not).

## 9. Acceptance

1. Fresh defaults, empty My Apps: point at Oryne in the Simulator → `fix`; point at a Debug build of Locant itself → `fix` with `Project:` set; point at Figma → `reference`.
2. ⌘, from the menu bar opens Settings; it passes the side-by-side test with System Settings.
3. Change the hotkey to Option; ⌥⌥ opens the overlay, ⌃⌃ does not.
4. Choose a different folder; the next capture lands there.
5. The ball rests, docks, wakes at approach, and a click opens the overlay with the front app's context; Esc returns it to rest. It never appears in a capture.
6. Toggle the ball off in Settings; it disappears and stays off after relaunch.
